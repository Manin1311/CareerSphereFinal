04. Database Architecture — SQLite via Django ORM
Schema Design · Models · Relationships · Indexing · JSONField Usage
Why SQLite?
CareerSphere uses SQLite as its primary database, accessed entirely through Django's ORM layer. SQLite is an embedded, serverless, zero-configuration relational database engine that is bundled with Python's standard library. All database access goes through Django's ORM — meaning the system can be migrated to PostgreSQL or MySQL simply by changing the DATABASES setting in settings.py, with zero code changes required. For a full-stack portfolio and demo deployment, SQLite provides the perfect balance of simplicity, reliability, and feature completeness.

⚡ Zero Configuration

No separate database server process required. The entire database is a single db.sqlite3 file in the project root. No connection string, no credentials, no port configuration needed.

🐍 Built into Python

Python's standard library includes sqlite3 module. No additional installation step is required. Works identically across Windows, Linux, and macOS — critical for the cross-platform install.bat script.

🔄 ORM Portability

All queries use Django ORM (not raw SQL). Switching to PostgreSQL for production requires changing one dictionary in settings.py. Django generates the appropriate SQL dialect automatically.

📄 JSONField Support

Django 3.1+ added native JSONField support for SQLite. CareerSphere extensively uses JSONField for storing parsed resume data, skill arrays, match details, and round configurations — all without needing a separate NoSQL store.

🔒 ACID Compliant

SQLite is fully ACID compliant (Atomic, Consistent, Isolated, Durable). All writes are transactional. Django's database transactions (transaction.atomic()) work identically with SQLite as with PostgreSQL.

📦 Single-File Backups

Backup the entire database by copying one file. For demo deployments and submission, this is far simpler than managing PostgreSQL dump files, pg_restore, and connection pools.

💡 JSONField — The Power Move

CareerSphere stores complex AI output (parsed resumes, match breakdowns, interview transcripts) directly in SQLite JSONFields rather than creating dozens of normalised tables. This simplifies schema evolution significantly: when the AI parser adds a new "certifications" section, no migration is needed — the JSON simply stores the new key. The trade-off is that JSONField columns cannot be indexed like scalar columns, but for read-heavy display use-cases in a portfolio project, this is a very acceptable design decision.
