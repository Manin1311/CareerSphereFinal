1. System Overview & Architecture
System Overview
Q1 What is CareerSphere and what core problem does it solve compared to existing ATS systems?
CareerSphere is an autonomous multi-agent recruitment and career intelligence platform. Traditional Applicant Tracking Systems (ATS) rely on basic keyword substring matching and fail on modern multi-column PDF resumes. CareerSphere solves this by using:
1. Geometry-Aware PDF Parsing: PyMuPDF bounding-box column splitting to parse multi-column resumes without scrambling text.
2. Semantic Vector Matching: Sentence-transformers (384-dimensional embeddings) and cosine similarity to match candidates on conceptual skill similarity, not exact word matches.
3. Autonomous Multi-Agent AI: 21 specialized agents handling resume parsing, skill normalization, interview question generation, and historical hiring ML predictions.
System Architecture
Q2 Explain the high-level architecture of CareerSphere.
CareerSphere follows a decoupled client-server architecture:
  • Frontend: Single Page Application (SPA) built with React 18, Vite, and Zustand for state management.
  • Backend: Django 4.x exposing RESTful APIs with custom JWT authentication decorators.
  • Database: SQLite managed via Django ORM using JSONField for semi-structured AI outputs.
  • Async Worker Queue: Celery backed by Redis for offloading long-running AI inference tasks.
  • AI Layer: RotateLLMClient managing pooled Gemini 2.5 Flash and Groq Llama 3.3 70B API keys with automatic failover.
2. Frontend Architecture (React 18 + Vite)
Frontend & State Management
Q3 Why did you choose Zustand over Redux or React Context API?
We chose Zustand because:
1. Zero Boilerplate: Unlike Redux, Zustand does not require action types, reducers, or provider wrapping.
2. Built-in Persistence: Provides a lightweight persist middleware that automatically synchronizes state (JWT tokens, user info) with localStorage.
3. Selective Re-renders: Components subscribe only to the specific slices of state they use, preventing unnecessary component re-renders across the app.
Frontend Routing & Performance
Q4 How is performance optimized in the React frontend?
Performance optimizations include:
  • Code Splitting: Heavy modules like ResumeEditor.jsx (102KB) and MockInterviewPage.jsx (70KB) are lazily loaded using React.lazy() and Suspense.
  • Vite Bundling: Sub-second HMR during development and optimized Rollup chunking for production.
  • Pure SVG Charts: Circular match score rings on job detail pages use native SVG stroke-dashoffset math instead of heavy charting libraries.
3. Backend Architecture (Django + DRF)
Backend & Auth
Q5 Why did you use Function-Based Views (FBVs) with custom decorators instead of DRF Class-Based Views?
Custom FBVs with explicit decorators (@require_seeker_jwt, @require_recruiter_jwt) provide granular control over token validation, error payload customization, and request object injection. It avoids hidden framework magic in DRF class mixins and makes token verification explicit and easily auditable.
Async Architecture
Q6 Why do you use Celery and Redis? What happens if a resume parse request is submitted?
AI resume parsing and scoring take 2–5 seconds per file. If done synchronously in the Django request thread, the web server would block, leading to browser timeouts under concurrent load.
Flow: When a user uploads a resume, Django saves the file, creates an IngestJob record, dispatches a Celery task via Redis (parse_resume_async.delay()), and immediately returns an HTTP 202 response with a task ID. A background Celery worker picks up the job, runs PyMuPDF layout extraction and LLM parsing, updates SQLite, and the frontend polls for completion.
4. Database (SQLite via Django ORM)
Database Choice
Q7 Why did you choose SQLite for CareerSphere? Isn't PostgreSQL better for production?
SQLite was selected because:
1. Zero-Configuration & Portability: Bundled with Python standard library. The entire DB is a single db.sqlite3 file, making local installation seamless across environments via install.bat.
2. Native JSONField Support: Django 3.1+ supports JSONFields natively in SQLite, allowing us to store parsed resume trees and match details directly.
3. ORM Layer Abstraction: All queries use Django ORM. Switching to PostgreSQL for production scaling requires changing only the DATABASES setting in settings.py with zero code modifications.
Database Schema & JSONField
Q8 When do you use standard relational fields versus JSONFields in your models?
We use Relational Fields (ForeignKeys, indexed CharFields) for entities requiring fast filtering, joins, or strict relational integrity — such as JobApplication.status, Candidate.match_score, and user references.
We use JSONFields for dynamic, semi-structured AI data that evolves frequently without needing schema migrations — such as parsed resume sections, skill arrays, interview transcripts, and AI match breakdowns (match_details).
5. AI & Machine Learning Implementation
LLM Reliability
Q9 How does RotateLLMClient prevent rate limit (429) failures during LLM calls?
RotateLLMClient is a thread-safe singleton manager that maintains pools of Gemini and Groq API keys.
  • Quota Tracking: Tracks daily usage counters per project and performs lazy resets at midnight Pacific Time (matching Google's quota clock).
  • Automatic Failover: When a key encounters a 429 Rate Limit error, the client parses the retry duration, marks the key as exhausted, and automatically retries the request using the next available active key in the pool.
  • Provider Fallback: If all Gemini keys are exhausted, requests automatically fall back to Groq (Llama 3.3 70B).
Matching & Embeddings
Q10 How does the candidate-job matching algorithm work mathematically?
The matching algorithm operates in three layers:
1. Vector Embedding Cosine Similarity: Skills are converted into 384-dimensional vector encodings using sentence-transformers (all-MiniLM-L6-v2). Cosine similarity is computed between candidate skills and required skills. Skills with similarity > 0.72 are marked as matched.
2. TF-IDF Fallback: If vector embeddings fail, a character n-gram (3–5) TF-IDF vectorizer runs with a 0.60 similarity threshold.
3. Weighted Formula & ML Blend:
Score = (Skill * 0.5) + (Experience * 0.3) + (Location * 0.2)
If ≥10 historical applications exist, a RandomForestClassifier trained on past hiring outcomes predicts hire probability, blending 20% ML prediction into the final score.

During your project viva, emphasize that CareerSphere is built on an **Asynchronous-First, Resilient Multi-Agent Architecture**. Even if external LLM APIs experience rate limits, the system's local mathematical algorithms (TF-IDF, cosine similarity, RandomForest) and LLM key-rotation pools guarantee 100% platform availability.
